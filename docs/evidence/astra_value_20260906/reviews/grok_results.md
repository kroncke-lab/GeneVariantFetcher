**Decision now: do not put Astra in the automatic regular protocol.** Zero incremental accepted count is enough to reject routine inclusion under the actual production gate, the user’s API-cost constraint, and this panel. It is not evidence that Astra cannot read sources, cannot ever help, or has been measured against a human or population ceiling.

The cleaner deploy-now result is the Grok 4.3 baseline audit, not the 180-second availability table. Of 24 positive questions, 16 already match the retained protocol on a comparable endpoint, one is the same interpretive `affected=2`, four documented-relative carriers are recovered by **both** successful Grok 4.6 arms and Astra, and three answers are a different cohort or phenotype. None of Astra’s nine “unique” values versus timed-out Grok 4.6 is a new accepted regular-protocol count. Faster completion does not change that.

## Material flaws and overclaims

**1. The primary scoreboard is mostly a timeout instrument, not an extraction contest.**
Under the shared 4,096-token / 180-second package, Astra finishes 7/8 papers and 22/24 numeric references; Grok finishes 2/8 then 3/8. Wrong non-nulls are 0 in every arm. Failures never earn null credit, so Grok’s 6/19 correct nulls are missing slots, not a hallucination rate. Quoting 7/8 vs 2/8, or 22/24 vs 4/24, as model quality is a misuse of the design. The nine Astra-only numbers sit on three papers where **both** Grok calls timed out.

**2. Zero accepted increment is the right production metric and a weak model metric.**
Literal-validator accepted counts are 0 / 0 / 1 in the primary arms and 1 / 1 after remediation, and that single accepted field already exists in the Grok 4.3 baseline. If the validator is the live gate, paying more for extra raw numbers that never ship is not routine value. If the validator is too tight, this experiment has almost no dynamic range: every reader looks the same. Numeric agreement is not clinical acceptance; source-binding is not cohort, timepoint, or role correctness. The report states this, then still lets “exact numeric references / 24” read like an accuracy leaderboard.

**3. The fallback sentence overstates unreplicated benefit.**
“Optional source-reading fallback for human review” is a policy preference, not a measured yield. Production already uses the ordinary 1,200-second timeout. The stall pattern that made Astra look uniquely available was the diagnostic 180-second cap. After the cheaper-reader package, an Astra missing-only overlay adds **zero raw numeric answers and zero accepted counts**. This panel does not show that a timed-out cheap call, retried with Astra, would add accepted protocol counts. Medium-effort “no count advantage” is a different test and should not prop up the fallback.

**4. The 5.42× ratio is not a clean model price.**
It is returned-proxy cost on **seven** papers where **both heterogeneous packages** completed with known usage: Grok remediated (inline schema, `json_object`, 8,192 tokens, 1,200 seconds) versus Astra original (provider schema, 4,096, 180 seconds). It drops Astra’s failure, is not whole-paper pricing, is not an invoice, and is not a speed ablation. Two scheduling amendments plus Azure aggregates that do not isolate queueing, reasoning, or schema overhead mean 13 s vs 324 s is an observation, not a controlled latency result. The lead sentence “Astra costs 5.42 times as much, with no additional accepted count” is true only inside those qualifications.

**5. Remediation is being asked to do more work than it can.**
It is a post-hoc package, not a one-factor ablation and not unchanged production (production does not explicitly request `json_object`). It is still useful as a check that the apparent Astra-only numbers were not uniquely Astra-readable. It does **not** prove that production Grok 4.6 would have recovered them, and the routine-use decision does not need that proof because the retained 4.3 baseline already holds the comparable accepted content.

**6. These tests cannot support a human ceiling, corpus uplift, or general accuracy rate.**
Eight opened, selected, within-paper-clustered questions; investigator-supplied variant, population, and endpoint; no zero-reference questions; no holdout; one interpretive field carved into a 42-question sensitivity. Do not report 17/24, 22/24, 24/24, or 42/42 as protocol accuracy. Do not treat 43 questions as 43 independent trials. No population or human ceiling follows, including any “75% of human” figure.

**7. Residual ways the write-up can still be quoted wrongly.**
“Astra can read difficult source material and sometimes completes when Grok 4.6 stalls” is configuration-true and easy to cite as reading superiority. “Keep Astra out of the automatic regular protocol” is easy to cite as “Astra failed.” Both need the deploy-now / never-help split in the same sentence.

## What bounded use is actually supported

Supported:

- **Do not change the default** on this evidence. No unopened tranche, validator, or extraction default should move.
- **Do not pay Astra routinely for count extraction** when the live gate is the current literal validator and the user is spending a nearly exhausted ~$150 API envelope (conservative **$149.4599652 / $150**; no new budget; CLI excluded; Anthropic extraction credits unused and finite).
- **Treat Astra’s demonstrated advantage here as faster completion under the tested packages**, not as added accepted coverage.
- **Treat the cheaper-reader package as a check** that the nine Astra-only candidates were recoverable by Grok when the call could finish, not as a production A/B.

Not supported:

- Automatic timeout-only routing to Astra.
- A claim that Astra is useless, cannot read hard PDFs, or will never add a count on other papers or contracts.
- A claim that Grok 4.6 is slower in a controlled sense, or that 5.42× is the production multiple.
- A claim that human review of Astra output has been shown to raise accepted yield.
- Any human, population, or corpus-uplift headline.

If a later system has a hard interactive latency budget that 300-second Grok completions miss, that is a different product decision. This pipeline, with a 1,200-second ordinary timeout and a validator that admits one already-known field, is not that product.
